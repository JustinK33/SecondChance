# The curated program catalog

This directory holds the facts SecondChance is allowed to state about real assistance programs.
It is data, not content: every record is read by the deterministic eligibility engine, and every requirement a user sees is rendered from the `description` text on a condition in one of these files.

If a record here is wrong, the product confidently tells a person something untrue about help they are counting on.
That is the worst failure this system can have, so the rules below are not negotiable.

## Rules for this directory

1. **Nothing is invented.**
   Every threshold, URL, phone number and excerpt comes from the official page of the administering body.
   If the official page does not state an income limit, no income condition is encoded - the gap is written into `limitations` instead.
2. **Every requirement carries its receipt.**
   Each condition's `source_ids` point at entries in the same record's `sources` list, and each source carries a verbatim `excerpt`, a `retrieved_at` timestamp and a `content_hash` of the page text at fetch time.
3. **Only `VERIFIED` records may support an eligibility claim.**
   A record is `VERIFIED` when the official page was fetched and the excerpt genuinely supports the encoded rules.
   It is `NEEDS_REVIEW` when the page was reachable but the requirements were ambiguous, and `UNVERIFIED` when the page could not be fetched at all.
   Anything other than `VERIFIED` has `active_rule_version: null`, which makes `AssistanceProgram.supports_eligibility_claims()` return `False` - so the program is still shown as a useful resource link but is structurally excluded from any assessment.
4. **The engine decides the status; the model only writes language.**
   Nothing in these files is generated by a language model.
5. **No personal data, ever.**
   These files describe programs, not people.

## File format

One file per `ProgramCategory`, named after the category. Each file is:

```json
{
  "category": "FOOD",
  "description": "one line about what this file holds",
  "programs": [
    {
      "program":      { "...": "an app.schemas.program.AssistanceProgram" },
      "rule_version": { "...": "an app.schemas.eligibility.RuleSet, or null" },
      "limitations":  ["what this record does not cover"]
    }
  ]
}
```

The wrapper exists because `AssistanceProgram` deliberately has no slot for an unapproved rule set or for `limitations`: those belong to a *view* of a program rather than to the program itself.
`program.active_rule_version` names the `RuleSet` in force and may only be set when that rule set is `APPROVED` and the program is `VERIFIED`.

Conventions that the loader and the tests both enforce:

- `program.id` must equal `uuid5(PROGRAM_NAMESPACE, slug)`, so the seed script, the fixtures and the database agree without a lookup table.
- `slug` is unique across every file.
- `sources[].id` is **globally** unique across every file. `program_sources.id` is the table's primary key and each row belongs to one program, so two programs citing the same document need one source entry each - see the four `njbpu-*-income-limits-2026` entries, which quote the same NJBPU table for four different programs.
- Every condition has a non-empty `description` written for a reader, and at least one `source_ids` entry.
- Every URL is `https` and on a recognised official domain.

## Loading it

```bash
make seed                                 # validate, then upsert into Postgres
python -m scripts.seed --validate-only    # parse and cross-check, do not open the database
python -m scripts.seed --dry-run          # do the writes inside a rolled-back transaction
```

`scripts/seed.py` validates every record against the Pydantic models *before* it opens a connection, upserts programs and sources on their primary keys, deletes sources a record no longer cites, and inserts a new rule version only when the rules actually differ from the newest stored version.
Re-running it reports `unchanged` for everything.
When the rules do change, the previous version row gets an `effective_to` and a `SUPERSEDED` status and a bumped version is inserted, because an evaluation recorded last month still has to be explainable against the rules that were in force then.

## Checking that it is still true

```bash
python -m scripts.verify_sources            # re-fetch every source and compare hashes
python -m scripts.verify_sources --offline   # age report only, no network
python -m scripts.verify_sources --strict    # exit non-zero if anything is dead, changed or stale
```

**`verify_sources.py` is an operational script and must never run inside a web request.**
It makes dozens of outbound calls to government and nonprofit sites; running it per-request would add tens of seconds of latency, hand a caller an SSRF-shaped amplifier, and get us rate-limited by the agencies the product depends on.

The content hash is taken over *normalised visible text* - scripts, styles and markup stripped, entities unescaped, whitespace collapsed - rather than the raw response body, so a rotating CSRF token or a reformatted template does not masquerade as a policy change.
`CHANGED` means a page we rely on was edited: re-read it, and if a requirement moved, bump the rule version rather than editing the one already in force.

Freshness buckets come from `app.schemas.program.compute_freshness`: `FRESH` under 90 days, `AGING` to a year, `STALE` beyond that.
Stale sources are excluded from eligibility claims, so the `STALE` list is the re-verification queue.

## Known gaps in the current data

These are real limits of the encoding, recorded here as well as in each record's `limitations` so they cannot be lost:

- **County-by-household-size income tables are not encoded.** SRAP and the Section 8 Housing Choice Voucher publish an income limit for every county and household size. The rule DSL has no condition for a two-dimensional table, and encoding 21 counties by 8 sizes as nested conditions would be unreviewable. Both programs encode geography only and surface the gap as a limitation, so they resolve to a preliminary match that is deliberately broader than the programme.
- **Programs with published limits the engine cannot see.** Asset and resource limits (SNAP, Charity Care, CCAP), base-year wage history (Unemployment Insurance) and filing status (NJEITC) are all real requirements that the profile does not capture.
- **Household sizes above eight.** The NJBPU utility table stops at eight people, so USF, LIHEAP, PAGE and Lifeline cannot screen a larger household rather than guessing at an extrapolation.
- **Federal poverty level year is pinned to 2026.** `IncomeFplCondition.fpl_year` is set to 2026 for every record, because the official pages cite "the federal poverty level" without naming a year. When the guidelines are updated, the FPL table and these records must move together.
- **NJ 211's published number is `2-1-1`,** which is shorter than the catalog's phone field allows, so it appears in the summary text instead.

## Programs we looked for and did not include

- **Low Income Household Water Assistance Program (LIHWAP).** No live official New Jersey page could be found; every candidate URL under `nj.gov/dca` returned 404. Water bill help is instead represented through the SHARES water programmes and the Winter Termination Program, which does cover water and wastewater shut-offs.
- **Summer EBT / SUN Bucks.** No live official New Jersey landing page could be found. The Summer Food Service Program, which is live and documented, is included instead.
- **The Middlesex County Board of Social Services' own website.** It blocks automated access, so the record is sourced from the New Jersey Division of Family Development's official county agency directory. Contact details should be confirmed by phone.

## Adding or changing a program

1. Fetch the official page and read it. Do not work from a third-party summary.
2. Quote the passage that supports each rule into a `sources` entry, with the real fetch time and a content hash computed the same way `scripts/verify_sources.py` computes it.
3. Encode only what the page states. Put everything else in `limitations`.
4. Write `plain_language_summary` for somebody who has never heard of the programme, at roughly an eighth-grade reading level.
5. If you are changing the rules of a program that already has an approved rule set, add a new version - do not edit the old one.
6. Run `python -m scripts.seed --validate-only`, `pytest tests/unit/test_program_data.py` and `python -m scripts.verify_sources --offline`.
